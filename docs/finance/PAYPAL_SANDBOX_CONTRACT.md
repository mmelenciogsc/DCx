## Implemented sandbox operations

- Fixed origin: `https://api-m.sandbox.paypal.com`.
- OAuth: `POST /v1/oauth2/token`, HTTP Basic client credentials and `grant_type=client_credentials`.
- Webhook evidence: `POST /v1/notifications/verify-webhook-signature` with `auth_algo`, `cert_url`, `transmission_id`, `transmission_sig`, `transmission_time`, `webhook_id` and the exact parsed event; admitted results are `SUCCESS` and `FAILURE`.
- Verified subscription mapping: the immutable event object sent for verification is mapped only after `SUCCESS`. Exact documented lifecycle resource/status/plan fields bind a subscription to one configured plan. A US$3 completed sale requires that prior binding and records its sale ID. Refund/reversal events must resolve through that sale and cannot exceed its gross or aggregate recorded receipts.
- Verified dependency quarantine: only a successfully verified, strictly mapped sale/refund/reversal whose required subscription or sale binding is absent is durably retained. Schema v10 stores normalized bounded fields and digests rather than the raw body or verification evidence. Local bounded reprocessing performs no provider request, applies sales before corrections, uses capped backoff, and blocks conflicts, tamper and now-invalid events without ledger mutation. Aggregate health reports only stable state/count/retry/time fields and contains no provider or subject identifier.
- Durable operations bridge: server code maps that aggregate health into the provider-neutral operations contract with processing capability disabled by default. When explicitly enabled, exact reviewed state, approval, at most 100 due records, all accounting/quarantine transitions, resulting health and result validation share one non-deferred SQLite transaction. Independent connections to the same database serialize; stale review, replay and simultaneous duplicate submission fail closed, while any later-record error rolls back the whole batch. Processing reports and makes zero provider calls. This is not an authenticated endpoint or distributed-service lease.
- Simulation transport: a separately gated literal-loopback API requires a configured operator-token digest and separate non-authorizing operator-pseudonym digest; mutation has another explicit enable gate. Bounded closed-schema aggregate JSON, fixed-time token checks, per-peer limiting, hardened client origin/transport policy and response revalidation are tested through child Kestrel. Valid process decisions append minimized chained evidence, with success in the same finance transaction and unexpected failure rolling both back. Normal desktop mode remains unavailable. The fixture is not production identity, TLS, MFA, secret custody, centralized externally anchored audit or deployment evidence.
- Aggregate monitor: a further default-off gate polls only the aggregate health contract on a bounded interval. Schema v10 atomically appends fixed scheduled/due/blocked/recovered records to a chained aggregate outbox and binds sink success through immutable gap-free delivery receipts. Pending delivery survives restart with at-least-once semantics. It has no process path, provider call, external notification, human acknowledgment, escalation or disposition authority.
- Payout submission: `POST /v1/payments/payouts` with stable sender batch/item IDs and exact USD values.
- Reconciliation: `GET /v1/payments/payouts/{provider-batch-id}` with items requested. Batch states are `DENIED`, `PENDING`, `PROCESSING`, `SUCCESS` and `CANCELED`.

The production class exposes sandbox behavior only. Live payout mode has no transport path. An approved item binds an immutable recipient-snapshot ID and destination digest; both the eligible directory record and returned provider receiver must match it. The local owner workflow stores the exact email and binding in current-user Windows Credential Manager with minimized index metadata, but performs no PayPal request and always returns provider verification and eligibility as false. Responses remain untrusted until strict shape, identity, receiver, item and amount checks pass. Completed mixed outcomes post only successful items and hold failed amounts in contributor payable without creating a retry. A separately approved expiring review can reserve one distinct sandbox batch containing only exact unsuccessful items and replacement recipient bindings. Immutable source/target lineage and authorization markers prevent successful-item inclusion, duplicate remediation and restart/completion after missing lineage. A later lookup never resubmits a terminal batch and admits only one-way successful-item transitions to exact `RETURNED`, `REFUNDED` or `REVERSED`, with immutable adjustment evidence and a balanced compensating journal.

## Acceptance boundary

The local handler-backed tests establish serialization, validation, idempotency and accounting behavior without contacting PayPal. They establish same-database transactional replay, minimized chained operator-decision evidence, a read-only aggregate transition monitor and an authenticated loopback simulation process boundary, including approval/stale/replay denial, but not production transport or identity. The generated-data CARE operations window establishes only keyboard/UIA review against a credentialless fixture; normal mode remains unavailable. These tests do not establish production identity/MFA/TLS/centralized audit, distributed fencing, durable scheduling/external notification, account Subscriptions/Payouts capability, recipient eligibility, correct provider webhook configuration or regional/legal compliance.

Credentialed sandbox acceptance is blocked pending owner authorization and credentials. Before it can run, DCx also needs approved exact US$3 product/plan configuration, evidence of merchant/Payouts and recipient eligibility, an approved provider-verification/retention policy, real identity/MFA/TLS/secret custody/role lifecycle/centralized externally anchored operator audit, distributed fencing, production scheduling/alerts, and an approved accessible disposition/notification workflow. Remediation, quarantined replay and later-return mechanisms still require credentialed sandbox acceptance. No real payment, payout or subscription should be initiated from this implementation.
