# Threat model

## Protected assets

User files and prompts; browser sessions; API/OAuth/PayPal credentials; private CKB/CCB; Windows input/focus; local process authority; global signing keys and catalog; contribution provenance; usage receipts; entitlement and CARE ledgers; payout approvals; audit evidence.

## Trust boundaries

| Boundary | Untrusted side | Trusted enforcement |
|---|---|---|
| WebView2 content ↔ client | Web pages, scripts, downloads, DOM text | Origin-aware browser adapter and download quarantine |
| Documents/media ↔ parsers | Files, URLs, embedded objects, OCR text | Type/size limits, sandboxing, safe parsers, output validation |
| Model output ↔ tools | Prompt injection, hallucinated arguments | Typed schemas, policy engine, capability grants, evidence checks |
| UI ↔ Windows broker | Agent action requests | Allowlists, safe argument binding, focus lease, approval/cancel |
| Client ↔ OpenAI | Optional approved task payload | Redaction, minimization, protected key storage, TLS, cancellation |
| Client ↔ global service | Catalog updates/contributions/receipts | Signatures, nonce/idempotency, minimization, quarantine |
| Global service ↔ PayPal | Webhooks, entitlements, payouts | Signature verification, reconciliation, owner approval, sandbox first |

## Priority threats and required controls

1. **Prompt injection causes an OS or financial side effect.** Content-derived instructions have no capabilities. The policy engine requires a typed user-intent grant; destructive, external, privileged, publishing, and financial actions require accessible confirmation.
2. **Focus theft or conflicting input harms the user.** A single control coordinator issues revocable agent focus leases. Any user input pauses agent input. Handback restores a recorded UIA element when safe and otherwise announces a deterministic fallback.
3. **Browser session theft.** WebView2 profiles are DCx-owned, ACL-protected, and never created from Chrome cookies. Secrets are excluded from logs, artifacts, screenshots, crash reports, and model context.
4. **Command injection.** Brokers use executable plus argument-array contracts, canonical paths, workspace scopes, time/output limits, and deny shell interpolation by default.
5. **Malicious dependencies or community code.** Pin packages, record hashes/licenses/SBOM, scan, build in quarantine, test permissions, sign approved artifacts, support revocation.
6. **Tampered global updates.** Verify a pinned trust root, manifest signature, artifact digest, monotonic version, expiry/revocation, and atomic swap; preserve rollback.
7. **Private-data exfiltration.** Upload defaults off. Contributions require item-level preview, ownership attestation, redaction and secret/PII/license scans. Telemetry excludes prompts and source content.
8. **Receipt/payout fraud.** Entitlement-bound signed receipts, replay prevention, anomaly checks, audit sampling, immutable journal semantics, double-entry reconciliation, holds, and final owner approval.
9. **Local denial of service/cost runaway.** Per-task token, time, memory, process, network and retry budgets; model unload; cancel/kill only the scoped child process.
10. **Confused-deputy elevation.** The main app runs unelevated. A future elevation helper must be narrowly scoped, short-lived, separately authenticated, and invoked only after explicit consent.

## Implemented OpenAI/Codex controls through P04

- The child environment is rebuilt from a small OS-variable allowlist; arbitrary parent secrets are not inherited.
- DCx uses an isolated per-user `CODEX_HOME` and ephemeral app-server auth storage, so it does not copy or silently reuse the developer's Codex/ChatGPT session.
- API keys live in Windows Credential Manager, never command arguments or project files. Known values and bearer credentials are redacted from bounded child diagnostics.
- P04 threads are ephemeral and read-only; web search, apps and multi-agent features are disabled. Unhandled server tool requests receive no authority.
- Before `turn/start` dispatch, user cancellation prevents the request. After dispatch, DCx retains the bounded identity-bearing response path even if an active-turn notification arrives first, then interrupts only the exact returned thread/turn identity. App-server lifetime cancellation and request timeout remain enforced, preventing cancellation from orphaning a known active turn through notification/response reordering.
- Commercial ChatGPT-plan sign-in remains compiled unavailable until eligibility is evidenced. A model catalog is never considered authorization.

## Implemented BOSS controls through P05

- Task graphs reject duplicate/unknown dependencies and cycles before execution.
- Routing is capability- and privacy-constrained with deterministic-first precedence; unavailable private tasks do not silently route to OpenAI.
- Evidence, attempt, elapsed-time, task-token and aggregate-token gates fail closed. The aggregate breaker prevents later capability execution after overrun.
- Checkpoints record decision metadata and measurements but omit task prompt/output bodies.
- Capability exceptions are classified without persisting exception messages that could contain private content.

## Implemented local-model controls through partial P06

- Ollama owns a loopback-root-only HTTP transport with redirects, cookies and proxies disabled. Every response must remain on the exact approved scheme/host/port. Model names/digests/capabilities, prompts, admitted PNG/JPEG/WebP images, embedding batches, vector dimensions and JSON responses are bounded; malformed inventory, mismatched/incomplete vision results and inconsistent/nonfinite vectors fail closed.
- Vision and embedding inference require exactly one digest-qualified inventory alias whose 64-hex digest, capability and inspected license-text SHA-256 match the approved selection immediately before and after execution. Mutable names, duplicate names, changed license text and a binding changed during inference fail closed. Loaded resource measurement and unload verification bind by digest because Ollama may canonicalize its process display name.
- Model capability and license metadata are inspected locally. A keyboard/UIA-accessible manager exposes exact identity and complete license text, requires an unchecked-by-default approval, resets approval after save and exposes no acquisition action. Selection respects measured VRAM/RAM budgets, excludes non-digest-bound identities and uses deterministic least-resource embedding preference.
- Per-user selection state contains only exact name, model digest, license digest and approval UTC. Ollama, Whisper and FFmpeg selection state plus aggregate benchmark evidence share one local, non-root storage guard: every existing directory ancestor, directory and present target must be non-reparse; paths are revalidated after open and immediately before atomic replacement; unsafe cleanup is abandoned rather than followed. Linked roots/files and settings/evidence directories swapped after open fail without writes through the link. Strict schema/size/name/hash validation still fails closed, and vision/embedding choices can be independently cleared. A same-user check/open race remains for production ACL/process isolation to address.
- Remote fallback requires connectivity plus separate provider approval and is unavailable for private input when no local backend exists.
- Whisper registration requires four distinct regular files on a local drive: executable, model and separate runtime/model licenses. Reparse files/ancestors, network/device paths, unsupported types and binary or oversized license text fail closed. The accessible review displays both complete licenses and exact byte digests; approval is default-off, invalidated by path edits and followed by a four-file save-time recheck. There is no download/install action, and clearing preserves the source files.
- Whisper executable, model and license files are SHA-256 pinned. Both license files are reverified before adapter creation. The executable and model are size-bounded and reverified for every run. Verified executable/model files and the signature-checked WAV input remain held by read-only, no-write/no-delete leases through process completion so they cannot be replaced between verification and use.
- Whisper runs without shell interpolation, with a scrubbed environment, typed arguments, timeout/tree kill, transcript size/reparse checks and deleted operation storage. Transcript bytes are held under a read lease, decoded as strict UTF-8, normalized for line endings and rejected on unsupported control characters before reaching the accessible UI. Child diagnostics and canceled partial text are never retained.
- FFmpeg execution requires the separately persisted exact executable/license/signature review. Processor creation revalidates the approved complete-license digest; every run revalidates the executable SHA-256 and holds both executable and signature-checked MP3/MP4 input under no-write/no-delete leases. Absolute paths, typed arguments, a scrubbed child environment, private random operation storage, timeout/tree kill, output-size limits and required WAV/PNG signatures fail closed. The leased output is deleted when the immediate Whisper or Ollama consumer finishes. No media consumer resolves FFmpeg from `PATH`.
- Transcription quality evaluation bounds fixture count/text and total edit-distance cells before work, normalizes deterministically and returns only aggregate WER/CER edit counts/rates. Embedding evaluation bounds corpus/query/dimensions, rejects nonfinite/zero/inconsistent vectors and invalid relevance labels, and returns only aggregate Recall@K/MRR. Both require elapsed and working-set evidence, optionally require GPU evidence, require unload by default, and use closed failure codes without returning transcript text, identifiers or vectors. Caller-supplied fixtures and thresholds remain untrusted until reviewed; evaluator success alone is not model acceptance.
- Benchmark execution requires a DCx-clock-validated explicit approval, at most 30 minutes old, over domain-separated backend/suite/policy digests. Strict bounded manifests reject ambiguous JSON, unknown fields, path escape/reparse/network inputs and duplicate WAV weighting. The keyboard/UIA surface shows exact digests, provenance/license and thresholds; starts approval off; revalidates the manifest, approved backend and suite before one run; and revokes approval after edits or termination. Transcription WAV bytes/length and expected text are rehashed under local no-write/no-delete leases; embedding text/relevance is rehashed and batched by 32. Backend binding is checked around every sequential call, unload is mandatory, substitution fails closed, and cancellation releases leases without replacing prior evidence. Revalidated atomic latest-only evidence omits paths/content/identifiers/vectors.
- The concrete embedding benchmark adapter binds approved model/license identity plus Ollama runtime version; rejects malformed version/running-model evidence and an already-loaded target; validates vectors and counters; samples one exact post-call `/api/ps` identity; and always attempts exact `keep_alive:0` cleanup under an independent timeout. Unload requires the exact completion response plus three consecutive digest-absence observations. Ollama `size` and `size_vram` are labeled loaded memory, not claimed as operating-system peak working set. A concurrent external Ollama client remains a possible attribution race, so a future real acceptance run requires an operator-controlled quiet period.
- Current Whisper and embedding successes are deterministic adapter fixtures, not accuracy or installed-backend evidence. P06 remains blocked pending approved binaries/models and real quality/resource benchmarks.
- Digest equality is local runtime byte identity, not publisher authenticity. The accessible approval manager handles only already-installed models; signed provenance, approved acquisition, installation and update/revocation policy remain absent.
- The authenticated dependency catalog deterministically expands the selected set into exact candidate, license and Ollama-layer source/length/digest identities. Exact-source conflicts fail closed, identical source identities are deduplicated without dropping their roles, and a domain-separated plan digest binds the full set and conservative two-copy-plus-512-MiB storage formula. Volatile free-space observations do not change that digest and unknown/insufficient capacity never passes. The UI exposes the exact plan plus a canonical redirect-policy digest and route inventory before a separate single-use unchecked transfer approval, and capacity is rechecked at execution.
- The local-dependency HTTP boundary does not trust a self-consistent plan alone. Production reloads the hash-pinned embedded catalog, re-derives the plan and requires an exact-item approval bound to the reviewed redirect-policy digest plus a passing capacity observation before sending. HTTPS platform trust remains mandatory. Automatic redirects, proxy use, credentials, preauthentication, cookies and decompression are disabled, and response-header size is bounded. Startup is canonical deny-all. An explicit user-invoked reviewer can issue only bounded HEAD requests and create a non-persisted two-hour schema-v2 session whose transitions bind item source/length/digest and exact query-free previous/target HTTPS URIs, never a host or directory prefix. Signed queries are transient and absent from authority/evidence. Missing, expired, changed or substituted sessions deny before a new payload request; a change during transfer removes partial output. Unsafe/relative targets, IP literals, loops and more than three hops are rejected; every hop uses a fresh credential/cookie/referrer-free identity/no-store request and verifies its response URI. Final status, declared length, range/encoding headers, streamed byte count and SHA-256 fail closed. A rejected destination is untouched. After an empty writable/seekable destination is admitted, every ordinary denial, cancellation, timeout, callback, transport/stream failure or content mismatch attempts unconditional truncate/rewind/flush. Unexpected cleanup failure produces only `dependency_transfer_cleanup_failed`; that destination is untrusted and the set coordinator removes its complete incoming operation directory. Stable public codes omit transport details. The separate command-line HEAD-only auditor remains evidence-only and cannot create a product session.
- The transfer-set coordinator binds both plan and redirect-policy digests in explicit set/item approvals, rechecks current policy and capacity before storage, confines random incoming content under non-reparse per-user roots, and accepts only exact item-result identities including policy digest. Its deterministic source-path-free schema-v2 receipt records the historical policy digest; current-user Credential Manager protects the complete receipt before atomic publication. Verification requires that protected fact and exact directory inventory, then rehashes every payload under a no-write/no-delete read share. A later policy change does not invalidate protected historical provenance or authorize reuse. Existing completed sets are immutable. One in-process gate serializes transfer, verification and cleanup. Operation failure/cancellation, including a progress-observer failure before commit, deletes only its own strict random incoming directory. After atomic publication or full verification, non-authoritative progress-observer failure cannot contradict the durable success result or trigger deletion. Recovery recognizes the strict name shape, refuses links and runs only while the product holds its exclusive data-root lease. Same-user code/races remain outside this boundary.
- The accessible workflow never contacts a provider automatically. **Observe current provider routes** is a distinct explicit action with its own cancellation and a notice that only public HEAD requests occur. Its result exposes counts, expiry, digest and every query-free transition but leaves transfer approval unchecked. One later unchecked exact-plan-and-policy approval enables one transfer and resets after every outcome. Retaining the displayed snapshots prevents changed policy from becoming silently approved at keypress. During payload work only cancellation remains available; item/byte progress omits URLs, paths and diagnostics. Completion is announced only after protected full-set reverification, and separate keyboard actions reverify or recover. Environment/root-gated native fixtures prove default-off approval, unique access keys, focus, policy review and cancellation with synthetic data and zero provider requests; they are not real acquisition evidence. Owner authorization, human AT, contained licenses and backend acceptance remain blocked.
- Native product hardware profiling uses `GlobalMemoryStatusEx`, runtime architecture, `DriveInfo` and bounded read-only machine registry keys. It executes no diagnostic process and returns no registry path or stable device identifier. Malformed text, implausible totals, more than 16 adapters and graphics-memory values without their source fail closed. The desktop uses the largest registry-reported graphics-memory value and physical RAM to apply the existing 70%/25% selection limits, then recaptures hardware and model inventory before save. These static values do not prove live available VRAM, GPU use or workload performance; benchmark resource/unload evidence remains mandatory.

## Implemented content controls through P07

- Local admission canonicalizes paths, rejects direct reparse files, applies per-kind size ceilings and verifies binary signatures before viewer/parser dispatch.
- Office ZIP/XML extraction caps entry count and expanded data, prohibits DTDs and external XML resolution, and never executes embedded code or objects.
- OCR-derived geometry and repaired semantics must validate before export; display-only content is not silently converted into an editable field.
- YouTube admission requires HTTPS, an exact supported host and a valid video identifier; credentials, lookalikes and unsupported page types are denied.
- Media does not autoplay. Local MP4 frame extraction and MP3/MP4 audio extraction require the exact user-approved FFmpeg binding and the leased processor controls above. Local and web frame questions use only the exact user-approved, digest/license-bound loopback Ollama vision model and leave playback paused for follow-up questions or user-controlled resume.
- The local-model manager can review and persist an exact existing FFmpeg executable/license binding with real Windows Authenticode status and default-off approval. The measured installed candidate is unsigned and remains unapproved outside disposable validation profiles. Native fixture UIA proves approved MP3 extraction composed with approved Whisper, clear-binding denial, and real local-frame extraction through an isolated approval; it does not establish production publisher, licensing, quality or performance acceptance.
- A web-frame request is an explicit user action against the current shared DCx tab. It selects only the largest ready, visible top-document HTML5 video, clips its finite bounded rectangle to the viewport, pauses it and captures only that rectangle. The page URL, browser profile and cookies are not model inputs, and there is no remote-model fallback.
- Page content, including text inside the captured frame, is untrusted evidence and cannot grant tool authority or override the visual-evidence-only prompt. Question length, geometry, playback time, image/base64 and response sizes are bounded. Random temporary image storage transitions from an exclusive writer to a read-only/no-write/no-delete lease; owned decoded image buffers are zeroed and operation storage is removed.
- Resume is a separate action bound to the same tab and page. Navigation, missing/hidden/unready video, invalid geometry, protected capture, unavailable or changed model identity, and provider-controlled playback fail with stable content-free states. The implementation does not traverse cross-origin frames, download provider media, copy cookies, or bypass DRM, advertising, login, MFA, age, region or rights controls.
- HTML/DOCX exports are newly generated semantic artifacts rather than modified untrusted source packages. Human review remains necessary before relying on OCR or model descriptions.

## Implemented private-knowledge controls through P08

- Private profile identifiers map to distinct hashed directories; databases, vectors and artifacts are never queried across those roots.
- Optimistic version checks and SQLite transactions prevent silent lost updates. Resource bodies and vectors are bounded and validated before insertion.
- Content-addressed writes verify declared SHA-256 and use same-directory atomic moves. CCB reads repeat artifact integrity, package identity and provenance checks.
- CCB ZIPs reject traversal, absolute/backslash paths, duplicates, symbolic links, excessive entry/expanded size, malformed manifests and missing entrypoints.
- CCB publisher trust is pinned by subject-public-key info. Canonical ECDSA signatures bind code digest and meaningful metadata; an untrusted publisher, changed body or changed package fails closed.
- Artifact packages are data, not executable authority. Only a host-registered adapter with matching identity/digest and passing bounded fixtures becomes a BOSS capability; package code is not dynamically loaded.
- FTS input is tokenized into a bounded parameterized expression. All relational writes and queries use parameters rather than concatenated user content.

## Implemented global-replica controls through partial P09

- Every canonical release is ECDSA-signed and binds its sequence, previous signed-release SHA-256 and resulting canonical-catalog SHA-256.
- Clients stage bounded chunks, preserve interrupted partials, verify descriptor digest/signature/chain/result, write immutable generation files and atomically replace only the active pointer.
- Wrong signatures and conflicting sequences fail before activation. Prior signed generations support explicit rollback after verification under the current trust policy; the protected floor deliberately does not pin the release sequence.
- A pinned offline P-256 root signs canonical trust-policy snapshots. Policies bind monotonically chained revisions and release-key SHA-256 identities, sequence windows and revocation points; a fresh client downloads every retained policy revision before accepting releases.
- Trust-policy history is durable in the authoritative SQLite registry and transferred in bounded digest-checked chunks. Stale/conflicting policy state, a non-root policy signature and a revoked release signer fail closed.
- The Windows client stores the highest accepted trust-policy revision, exact policy digest and trust-root digest in a strict per-user Credential Manager record outside replica files. A lower/missing/conflicting local policy fails closed. File-first/anchor-second updates recover only one signed predecessor-linked crash-window revision.
- A rollback target is verified under the current anchored trust policy before pointer replacement, so restoring older replica files cannot erase a recorded emergency revocation or corrupt the current active pointer. The anchor is not hardware-backed: same-user deletion of both credential and replica state, root custody/ceremony, anchor recovery, TLS identity and external review remain unresolved.
- Global replicas are keyed by trust-root hash under a separate `global` directory and never receive a private-store handle. Two-client tests preserve a private sentinel.
- Replica and authoritative registry roots, ancestor chains and operation-time release/catalog/staging/artifact/database/WAL/shared-memory files must remain local, non-root and non-reparse. The service accepts only the exact digest-derived artifact relative path and one exact P-256 signing key; linked roots/files, swapped directories and metadata redirection fail before use. This narrows path escape but does not eliminate same-user check/open races; production ACL/mount/service-account isolation remains required.
- Artifact metadata is signed with the catalog. Bodies remain lazy, content-addressed and size/digest verified; authoritative publication rejects missing artifact records.
- The HTTP client requires HTTPS except for literal loopback HTTP. The simulation server refuses startup without its explicit simulation flag, data root and external key file.
- Container context excludes secrets and runtime data; the Compose definition is read-only/non-root/no-new-privileges. It remains unexecuted because Docker access is blocked.

## Implemented contribution controls through partial P10

- Contribution preparation defaults off, and each changed item invalidates its prior review/approval digest and prepared object. Local preparation always yields quarantine. Intake, minimized status and withdrawal each have a separate initially unchecked approval and are restricted to the exact prepared object and one bound literal-loopback simulation origin.
- CCB selection admits one bounded regular non-reparse ZIP as an exact in-memory snapshot. The full path is cleared and never enters the candidate, transport or status; only the base name, SHA-256 and complete admitted text are shown for review. Manifest identity/version/license and artifact digest are bound into the candidate, and scanning covers the contribution body plus all admitted package text/test inputs.
- Rights/license/sensitive-data attestations, bounded approval age and unique nonces are revalidated at authoritative intake; client-provided scan results are not trusted.
- Scanner findings store only stable codes, not matched secrets or PII. Risky/dummy content cannot transition to approved.
- Approved CKB metadata enters the signed release path; withdrawal emits deprecation. The local server fixture permits a CCB transition only after exact package admission and passing authoritative sandbox evidence.
- Contribution HTTP routes are absent by default. Explicit simulation enablement requires distinct SHA-256 credential digests and bounded pseudonymous identities for contributor and reviewer roles. Bearer tokens are compared in constant time, transient token buffers are zeroed, contributor status/withdrawal is owner-scoped, and stable errors and process diagnostics exclude credential and contribution bodies.
- Enabled contribution routes are covered before endpoint work by a process-local fixed-window request and concurrency policy. Canonical direct-peer addresses become ephemeral SHA-256 partition keys; raw addresses and credentials are not retained or reflected. Partition count, configuration, timestamps and request leases are bounded/fail closed, but restart and multi-node coordination remain intentionally unsupported.
- The versioned contribution envelope rejects unknown metadata fields, undeclared/changed length, unsupported versions and content over the shared metadata/artifact/Kestrel bounds. Contributor identity is server-derived and must equal the reviewed candidate; reviewer identity is never accepted from the request.
- The Windows simulation client has fixed intake, exact-owner-status and withdrawal paths and rejects non-root, non-HTTP, host-name and non-loopback origins. Redirects, cookies, proxies and decompression are disabled; time/body limits, exact response origin/media type/submission/candidate/state bindings and strict JSON are enforced. Status omits candidate/body/findings and contributor/reviewer identities. A first attempt binds the origin; duplicate send remains disabled until that origin reports missing; cancellation/invalid results require reconciliation. Candidate identity is locked for an uncertain or accepted nonterminal lifecycle. CCB bytes remain only for reconciliation after an indeterminate result and are zeroed after confirmed intake/status, replacement, clearing or close; a missing server item after local clearing requires complete reselection/review/preparation. The bounded printable bearer token is cleared after each attempt and excluded from logs/persistence; owned metadata/envelope/request/artifact/response byte buffers are zeroed. Managed-string erasure is not claimed.
- A server-side rootless Bubblewrap prototype now executes hostile BusyBox-shell fixtures in separate user/mount/PID/network/IPC/UTS/cgroup namespaces. It drops all capabilities, clears environment, runs as 65534, exposes only digest-bound read-only package/input/runtime mounts, remounts root read-only and applies bounded CPU/address-space/process/file/descriptor/output/wall limits.
- Sandbox evidence binds the claimed artifact, canonical extracted workspace, test suite, policy launcher, Bubblewrap, runtime and output digests. Outside-quarantine paths, links/special files, digest substitution, host/system reads, external network, root writes, inherited secrets, timeouts and output floods fail closed in the local hostile gate.
- Exact schema-v2 package intake uses digest-addressed quarantine, identity/version/license and two-component CycloneDX/runtime closure, safe extraction, rescanning of every textual component and test input, all-test execution, durable minimized evidence, expected-output verification and signed artifact propagation. Tampering or a missing executor fails closed.
- Approval and withdrawal persist immutable reviewer-authorized intents before registry mutation. The registry atomically binds the digest-derived operation ID to a canonical change-set digest and release; startup validates a bounded batch and atomically advances local state/intent completion without duplicate releases. Recovery rehashes candidate and artifact data, while changed intent/candidate/artifact bytes fail closed.
- Pending intents have separate database-backed execution leases with random instance owners and fencing tokens, five-minute expiry/renewal and a 20-attempt ceiling. Claiming never changes the reviewed change set or grants authority. Completion requires the current unexpired token in the same transaction as state advancement.
- Concurrent local service instances claim a pending intent once. An expired worker cannot complete after takeover, malformed lease state fails before overwrite and the signed registry's stable operation ID remains the final duplicate-release defense.
- A second exact simulation gate enables a bounded hosted worker. It persists exponential retry and dead-letter state containing only operation/submission identifiers, stable failure code, bounded count and timestamps. Five transient failures or one permanent policy failure stops automatic work. Reviewer remediation reschedules the existing immutable intent and cannot change its authority or content.
- Worker health and minimized queue records are reviewer-visible. Candidate bodies, exception messages and stacks are absent; malformed persisted queue state fails closed. Requesting the worker without the authenticated simulation API prevents startup.
- CCB API approval requires that worker and persists a candidate-digest/reviewer-bound job before hostile execution. A separate 30-minute ownership-fenced lease exceeds the closed 32-test/30-second maximum; concurrent same-SQLite instances execute one claim. Sandbox mismatch, malformed job/lease data and 20 expired crash claims fail closed into body-free dead-letter state. Reviewer retry resets execution attempts but cannot change the immutable job.
- This is not yet a production publication boundary. Static digest-configured bearer roles, process-local limiting and same-SQLite polling are suitable only for a controlled loopback/container simulation; TLS ingress, production identity/rotation/revocation, distributed proxy-aware abuse controls, administrative audit UI, alerting, supported high availability, general dependency-lock/build profiles, seccomp, measured cgroup-v2 enforcement, immutable builder image, approved Ubuntu 24.04 deployment, monitoring and independent penetration testing are absent. A read-only audit confirms the real server has the expected base runtimes, but Docker access is denied, cgroup delegation is not writable and Bubblewrap network isolation fails for the authenticated user; no control may weaken network denial to work around that failure. The older direct in-process CCB approval method is retained for tests and must not be externally routed.
- Credit lineage rejects cycles, duplicate parents, invalid weights and total parent credit above 100%.
- Usage receipts contain identifiers, time and verification status only. Integrity, replay, entitlement, approved-resource, self-use, success, time and rate checks fail closed; client honesty is still treated as an untrusted signal.

## Implemented finance controls through partial P11

- Money uses checked integer cents. Journal entries must balance and conflicting event IDs fail closed.
- The defined contributor pool is zero for nonpositive net and rejected above 40% aggregate; allocation conserves exact cents deterministically.
- Sandbox fixture webhooks require integrity, bounded schema/identifiers and strict event/transmission replay semantics. Official-shaped events are parsed once, checked for duplicate JSON properties, mapped from the same immutable object sent for PayPal verification and admitted only after `SUCCESS`. Exact replay is idempotent; reuse of either identifier with different content fails closed, and rejected input does not poison an identifier.
- Entitlement state is reduced monotonically by signed occurrence time. Older events cannot overwrite newer state, and same-time deactivation dominates activation. Financial correction entries remain independent, so a stale refund/reversal can post and reconcile without regressing a newer entitlement.
- Payout execution requires sandbox mode, verified eligibility, explicit owner approval, Net 60 and a unique batch. Live mode has no provider path and always fails.
- SQLite schema v10 persists canonical event hashes, postings, webhook replay identifiers, minimized reducer decisions, entitlement provenance, exact subscription-to-plan and sale-to-subscription bindings, correction-object/cumulative receipt state, payout state, recipient snapshot/destination digest, per-item result, paid total, immutable later-return adjustments, failed-item remediation lineage, verified-event dependency quarantine, minimized operator-decision audit, aggregate alert outbox/delivery state and a unique local-to-provider batch reference with WAL and full synchronous writes. Migration preserves terminal state, quarantines legacy reserved payouts for reapproval and rejects unknown future schemas.
- The official-contract-shaped HTTP boundary is pinned to PayPal's HTTPS sandbox origin. Redirects, cookies, proxies and decompression are disabled; time, body, JSON depth and exact schemas are bounded. Stable errors exclude provider bodies, credentials and transport exception text.
- Sandbox client credentials are acquired through disposable owned byte leases and zeroed with request/response byte buffers. Basic/Bearer header values necessarily become transient managed strings and cannot be claimed as securely erased.
- Webhook verification requires all official evidence fields, an allowlisted PayPal certificate URL, duplicate-free event JSON and an exact official verification result. This does not authenticate anything until credentialed PayPal sandbox acceptance runs.
- Lifecycle resource type/status and the configured plan ID must match exactly. Payment cannot invent a subscription mapping; it requires a prior bound lifecycle event. Completed sales bind their provider ID, and refunds/reversals resolve through that binding, reject subscription substitution and cannot exceed either sale-level or aggregate recorded receipts. All mapping, accounting and event-ID writes share one transaction.
- Reserved payout batches retain canonical previews and SHA-256 digests. Each item binds a unique snapshot ID and exact destination digest; substitution is denied before credential use and provider lookup rechecks the receiver. Stable request/batch/item IDs and a durable provider reference prevent blind resend after provider acceptance. `PENDING`, `PROCESSING` and pending item states remain reserved.
- Recipient preparation requires the owner to review the exact contributor pseudonym, destination email and destination digest. Editing either input invalidates that review. Save and revoke use separate, default-unchecked approvals. The exact email and binding live only in a current-user Windows Credential Manager entry named by a random snapshot ID; the bounded JSON index holds only the pseudonym, digest, credential target, lifecycle state and UTC audit times. Two-phase pending-to-active writes, restart cleanup of orphaned pending credentials, active contributor/digest uniqueness, protected-secret/index comparison, reparse denial and revoke-before-delete behavior fail closed. The local directory performs no provider request and always reports provider eligibility as false.
- A provider batch `SUCCESS` becomes terminal locally only when lookup matches provider/local IDs, total item count, sender item IDs, receivers and USD amounts. Mixed terminal results post only successful amounts, keep failed amounts payable and persist an idempotent result digest plus exact item states; no automatic retry exists.
- Failed items are never copied automatically. A ten-minute review digest binds one terminal source result, a selected nonempty subset of unsuccessful source ordinals, exact amounts, the unchanged Net 60 date and replacement snapshot/destination bindings. Reservation requires separate owner approval and sandbox eligibility, and schema-v10 uniqueness permits only one remediation lineage per source item. Successful items, changed amounts, stale/tampered reviews and missing authorization lineage fail before provider use or accounting. Lookup-first restart recovery can resume only the same already-approved target batch.
- Only officially verified and strictly mapped sales/corrections may enter the dependency quarantine, and only for an absent subscription/sale binding. The record digest binds all normalized fields and the expected plan; raw provider bodies/evidence are not stored. Cross-table event/transmission collisions fail closed. Local reprocessing is capped at 100 due records, makes no provider call, orders sales before corrections, backs off repeated missing dependencies to at most one hour, atomically applies successful work and blocks nonremediable state. Digest tamper prevents audit, entitlement and ledger mutation. Its alert-ready health contract exposes only stable status, aggregate counts/retry depth and UTC times; identifier properties are structurally absent.
- The native CARE operations contract rejects malformed aggregate counts/times/state priority, processing capability without due work, outcomes above 100, unreconciled outcome counts and any nonzero provider-call result. Processing carries the exact reviewed health snapshot plus explicit approval. The normal source is unavailable and cannot imply a clear queue; the environment-gated fixture contains generated aggregates, no credential/transport and only one cycle. Its window defaults approval off, restores focus on denial, disables replay and labels the fixture prominently. This is not authentication or production authorization.
- The durable server-side contract bridge defaults capability disabled. When enabled, a non-deferred SQLite transaction covers rereading aggregate health, exact reviewed-value comparison, approval/capability checks, due selection, all bounded replay transitions, resulting-health reread and result validation. Separate repository connections to the same database serialize; stale/replayed duplicates fail closed, and any later-record error rolls back the whole batch. The result requires provider calls zero. By itself this is neither an authenticated endpoint nor fencing across separate databases/service replicas.
- The simulation process-boundary API is globally default off, separately gates API visibility and mutation, stores an operator-token verifier plus a separately configured operator-pseudonym digest, uses fixed-time authentication and privacy-minimized per-peer request limiting, and accepts only strict bounded JSON. Its client is restricted to a literal-loopback HTTP root, disables ambient redirect/cookie/proxy/decompression behavior and revalidates response origin/schema/invariants. The normal desktop cannot discover or instantiate it. Tests deny missing/invalid credentials, malformed input, absent approval, stale/replayed state, origin substitution, unknown fields and nonzero provider calls without logging token/body values.
- Only authenticated schema-valid process decisions enter the operator audit. Its record contains fixed action/decision codes, UTC, operator-pseudonym digest, reviewed aggregate/approval digest, optional aggregate-result digest and previous/current chain digests—never bearer tokens, bodies or event/provider/subject identifiers. Success shares the replay/accounting transaction; expected denials commit no queue/accounting mutation; unexpected failure rolls back both. Update/delete triggers and full-chain validation detect ordinary edits and gaps, but this is not an externally anchored immutable log: a database administrator can drop controls, recompute history or truncate the tail. Full-chain append cost, centralized export, access/retention, monitoring and production identity are unresolved.

It calls only aggregate refresh, validates every snapshot, serializes polls and emits fixed transition codes with aggregate counts. It contains no process method call, auto-approval, provider access, identifiers, body or exception text. Schema v10 atomically persists a digested aggregate observation and chained immutable alert record. Ordinary update/delete and content tamper fail closed. These shared-SQLite controls are not multi-database fencing or an externally anchored log. The fixed log sink remains validation telemetry rather than a production alert channel.

## Implemented package-install review controls through partial P12

- Package review accepts only a local regular `.msix`; the native validation route additionally confines it beneath a configured non-root fixture directory. Unsupported kinds, UNC/alternate-data-stream paths, missing/empty/oversized files and reparse files or ancestors fail closed.
- The exact package remains under a read-only/no-write/no-delete lease. Length, SHA-256, signature status, identity, publisher, signer-certificate SHA-256 and exact four-part version are checked when review begins and again immediately before recording approval. A canonical proposal digest binds those fields plus path/URI, typed operation, scope, no-elevation flag and ten-minute lifetime.
- The UI previews `PackageManager.AddPackageByUriAsync` and separate typed values rather than a caller-controlled shell command. Approval is initially unchecked, single-use and cancellable; stable errors exclude verifier exception text.
- This implementation deliberately has no executor. The receipt always says execution is not permitted and zero installer processes started. The process broker has no install operation, and automated UIA verifies that DCx starts no child process during denial, approval or cancellation.
- The successful native UI validation entry point is explicitly environment/root-gated and uses synthetic trust evidence. A separate read-only Windows path supplies real negative signature evidence as described under P13, but no owner-authorized signed-positive package exists. Neither path can install anything. One-time execution authority, final-file activation revalidation, rollback, clean-VM and human assistive-technology gates remain absent.

## Implemented release/recovery controls through partial P13

- Offline startup uses an embedded semantic document, permits its data navigation only as the first app-controlled navigation, and performs no website request.
- Backup scope is allowlisted to browser metadata and private knowledge. WebView2 profiles/cookies and Windows protected secrets are excluded.
- Backup and restore reject filesystem roots, reparse points, archives inside protected data, traversal/absolute/ADS paths, duplicates and size/count excess. SHA-256 and length are checked before any current data is replaced.
- Normal DCx holds an exclusive file lease scoped to its canonical data root. The separate recovery mode must acquire that lease for the whole backup or restore, preventing live SQLite/WAL copying and concurrent recovery operations.
- Restore requires a default-unchecked UI acknowledgment, stages content, and retains/moves prior roots for rollback. A denied operation does not create an archive or replace current data.
- Two self-contained `win-x64` publish trees and ZIPs are compared by path/length/digest. Repository text, DCx-owned published executables/assemblies and every published text/configuration artifact receive secret-pattern scanning. Synthetic hostile-input fixtures are allowlisted only in their two source test files. Random raw-byte matches in pinned Microsoft/runtime and NuGet binaries are not treated as secret proof; those binaries are controlled through exact inventory, notices, official advisory auditing and malware scanning.
- Release staging fails unless current Microsoft Defender protection is enabled and the canonical valid Microsoft-signed scanner returns clean for the exact publish tree, ZIP and unsigned MSIX with remediation disabled. The scanner child receives only five OS-derived environment values; arbitrary credentials, temporary paths and user context are not inherited. Scanner/certificate digests and minimized state are recorded, while console text is discarded.
- Direct and transitive managed dependencies fail the gate when the official NuGet audit reports any advisory. The JSON source, size, schema and request parameters are bounded, and zero-result plus affected-result fixtures guard the parser against absent-property miscounting.
- Crash capture is versioned-consent/default-off and records closed categories rather than exception content. Its six-field schema excludes messages, stacks, dumps, prompts, URLs, paths and identities; strict bounded atomic files remain local and retain at most 20.
- UI, task and process exception hooks do not mark exceptions handled or alter runtime failure semantics. Recording failure is swallowed only at the optional diagnostic boundary so it cannot prevent normal startup or mask the original crash.
- Accessible deletion preserves the current setting, while opt-out purges retained reports. No upload/export transport exists; local consent cannot authorize a future transfer.
- Read-only MSIX admission requires exactly one bounded root `AppxManifest.xml` in the Windows 10 foundation namespace and one valid direct identity. Entry count, manifest bytes and compressed bytes are bounded; case-variant duplicates, ambiguous/missing identity, invalid names/versions/namespaces, malformed XML and DTD/XXE fail closed.
- Windows Authenticode inspection uses the absolute built-in Windows PowerShell path, a constant encoded command, no profile or interaction, and a scrubbed child environment. The package path exists only in one process environment variable, not command text/arguments. Time, stdout and stderr are bounded; timeout/output flood kills the process tree; exception text and child diagnostics are discarded.
- Signature output is a strict closed JSON envelope. Only `Valid` plus an exact signer-subject/manifest-publisher match and lowercase signer-certificate SHA-256 can become trusted. Every other status or mismatch is denied. The real Windows probe denies both the original unsigned/incomplete fixture and the complete unsigned MakeAppx local-validation package; fixture-only positive composition is not signed-package acceptance.
- Local package construction resolves a pinned x64 Windows SDK MakeAppx outside `PATH`, rejects a reparse executable and requires a valid Microsoft Corporation Authenticode signer. Inputs and outputs are confined beneath the artifact root; payload reparse boundaries, overlapping/existing destinations and incomplete self-contained publishes are denied. Typed child arguments, a scrubbed OS-only environment, bounded diagnostics and a five-minute child limit constrain MakeAppx.
- Determinism canonicalization parses bounded ZIP/ZIP64 structures and rewrites only DOS timestamp fields. It fails closed on multidisk, truncated, excessive or inconsistent layouts. The resulting package must pass a second MakeAppx unpack and exact manifest/executable comparison, contain the expected block map/content types, contain no signature entry, report `NotSigned` and fail real trust verification. SignTool, package deployment and activation are absent.
- The payload embeds pinned .NET 10.0.12 runtime files plus notices, but deliberately does not bundle WebView2. Detection and environment creation request only the Stable/Evergreen release channel; actual version metadata must be a four-part numeric version so an override cannot silently select a suffixed Beta/Dev/Canary build. Missing or unverifiable runtime state exposes an assertive keyboard/UIA prerequisite region, disables browser commands while preserving independent local tools, creates no WebView2 profile, and offers only copy-address and local recheck actions. No download or installation authority exists; approved bootstrap behavior remains a release blocker.
- Controlled update admission requires canonical ECDSA P-256 metadata before package retrieval, exact HTTPS origin with redirects/cookies/proxy/decompression disabled, newer bounded four-part versions, short validity, exact length/SHA-256 and matching injected package signature/identity/publisher/version evidence. Digest and package trust checks share a no-write read lease; reuses are reverified and the package remains inert.
- The update core has only synthetic fixtures and is not wired to the application. The read-only Authenticode verifier has real negative Windows evidence but no authorized signed-positive fixture and is not an executor. Production signing-root custody/rotation, activation, installer transaction and rollback remain absent. A future activation path must reverify the exact final file and pass signed clean-VM lifecycle gates.
- These first-party point-in-time scans and unsigned-package checks do not replace code signing, independent security assessment, native-binary analysis, clean-VM lifecycle testing or human assistive-technology acceptance.

## Implemented readiness controls through partial P14

- A `GO` decision requires zero nonvalidated critical/major issues and a separate explicit production-activation approval. Approval cannot override a blocker.
- Readiness entries fail closed without a unique ID, owner role, next action and evidence reference. The current report assigns all seven critical/major blockers and remains `NO_GO`.
- The JSON report and native dashboard consume the same immutable current-readiness policy. The dashboard is read-only and exposes no production-activation, enrollment, collection, publishing or payment action.

## P11 opaque blocked-case review

- The random case reference, review digest, operator-pseudonym digest and timing remain sensitive linkable data. They are not anonymous.
- A case reference is created in the same immediate transaction that first blocks an event; schema-v10 rows are backfilled at schema-v11 startup in bounded batches. List requests use a deferred read transaction and cannot lazily create state.
- The authenticated API returns only closed event-kind/reason/disposition codes, attempt count, UTC times and the random reference/digest. Unknown fields, identifier-bearing response substitution, stale review digests, missing approval and nonzero provider/financial effects fail closed.
- Only `investigation_requested` and `retained_blocked` can be appended. Neither changes the blocked event, accounting or provider state. Free-form notes, replay/requeue, rejection, closure and financial commands are structurally absent.
- Binding and audit rows are immutable/append-only under triggers and a sequence-bound SHA-256 chain. These controls do not resist a privileged database administrator, provide production identity/MFA/TLS, deliver an external investigation notification, or define accounting-approved closure/requeue policy.
